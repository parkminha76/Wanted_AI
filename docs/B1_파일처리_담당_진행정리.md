## 1. 담당 범위

B-1의 담당은 **파일 형식을 다루는 모든 것**이다. PDF·DOCX·XLSX 같은 파일은 내부 구조가 완전히 달라서, 그 차이를 한 곳에서 흡수해야 뒤쪽 탐지기들이 형식을 몰라도 동작할 수 있다. 담당 파일은 파싱(`parser/`), 마스킹(`masking/`), 서식 기반 탐지(`detectors/hidden.py`)다.

추가로 오탐 제거 분류기의 학습·평가 데이터를 만들었고, 스캐너 전체를 검증하는 테스트 도구를 작성했다.

### 핵심 담당

- 파일 파싱 — 문서에서 텍스트와 서식 정보 추출 (`parser/parse.py`)
- 좌표 변환 — 글자 위치를 PDF 페이지 좌표로 번역 (`parser/locate.py`)
- 숨은 텍스트 탐지 — 흰 글씨·0pt·제로폭 문자 등 (`detectors/hidden.py`)
- 마스킹 사본 생성 — 원본 형식을 유지한 채 값만 가리기 (`masking/mask.py`)

### 추가로 진행한 범위

- 오탐 제거 분류기 학습 데이터 344건, 평가 데이터 120건 생성
- 숨은 텍스트 테스트 문서 36개 제작 및 임계값 8회차 조정
- 마스킹 검증 도구, 분류기 위치 버그 감시 도구 작성
- DB 판정 근거 코드(`hidden_reason`) 목록 정리

## 2. 완료한 작업

## 2.1 파일 파싱 (`parser/parse.py`)

파일을 열어서 **글자 전체(`raw_text`)와 조각별 서식 정보(`spans`)** 두 가지를 뽑는다. 이 출력 형식이 B-1과 B-2 사이의 유일한 약속이라, 첫날 고정한 뒤로는 서로 코드를 보지 않고 작업할 수 있었다.

### 지원 형식

| 형식 | 사용 라이브러리 | span 단위 |
|---|---|---|
| TXT / MD / CSV / LOG | 직접 처리 | 줄 |
| PDF | PyMuPDF | texttrace span |
| DOCX | python-docx | run |
| XLSX / XLSM | openpyxl | 셀 |
| 이미지 8종 | — (경로만 전달) | 없음 |

### 지킨 원칙 세 가지

**① 원문을 한 글자도 고치지 않는다.**
줄바꿈 정규화도, BOM 제거도 하지 않는다. 탐지 결과의 위치(offset)가 `raw_text` 기준이고 마스킹이 그 위치를 되짚기 때문에, 여기서 한 글자라도 손대면 화면 하이라이트와 마스킹이 전부 어긋난다.

**② span은 잘게 쪼갠다.**
숨은 텍스트 탐지가 "제로폭 문자 밀도"를 잴 때 분모가 문서 전체가 되면, 5만 자짜리 계약서에 200개를 심어도 0.4%로 통과한다. 그래서 줄·run·셀 단위로 쪼갠다.

**③ 모르는 서식 값은 "탐지가 안 되는 쪽"으로 채운다.**
색은 검정, 크기는 11pt로 채운다. 폰트 크기를 0으로 두면 "2pt 미만" 규칙에 전부 걸려서 멀쩡한 문서가 빨간불이 된다. 모르면 놓치는 게 낫지, 모른다고 신고하면 안 된다.

다만 배경색만은 예외로 `bg_known` 플래그를 따로 뒀다. "모르는 값"과 "진짜 흰색"을 구분하지 못하면, 흰 글씨를 무조건 신고하게 되어 흰 배경이 아닌 문서에서 오탐이 난다.

### 형식별로 해결한 문제

- **PDF** — `get_text()` 대신 `get_texttrace()`를 쓴다. 전자로는 렌더 모드와 투명도가 안 나오는데, 그 둘은 색·크기 검사를 통과하면서 화면에는 안 보여서 숨은 명령을 심기 가장 좋은 자리다.
- **DOCX** — 본문 문단만 읽으면 텍스트상자와 주석을 통째로 놓친다. 문단 API 대신 각 파트의 XML을 문서 순서대로 훑는다.
- **XLSX** — 엑셀 색 선택기에서 흰색을 고르면 RGB가 아니라 테마 색으로 저장된다. 테마를 못 읽으면 "흰 글꼴로 숨기기"를 전부 놓쳐서, `theme1.xml`을 직접 파싱한다.
- **스캔본 PDF** — 텍스트 레이어가 없는 PDF는 `kind="image"`로 표시해 이미지 파이프라인(신분증 CNN)으로 보낸다.

## 2.2 숨은 텍스트 탐지 (`detectors/hidden.py`)

AI 모델이 전혀 들어가지 않는 순수 규칙 검사인데, **기존 개인정보 검사 도구가 아예 다루지 않는 영역**이라 우리 서비스의 차별점이다.

### 탐지하는 것

- 흰 배경의 흰 글씨, 0pt·투명 텍스트
- PDF 렌더 모드 3 (글자를 배치하되 화면에 그리지 않음)
- Word 숨김 속성(`w:vanish`), 추적 삭제된 명령
- Excel 숨긴 행·열·시트, `veryHidden` 시트, 사용자 지정 서식 `;;;`
- 제로폭 문자, Bidi 재정의, Unicode 태그 문자

### 정한 원칙 두 가지

**① span 하나에 finding 하나.**
흰 글씨이면서 동시에 1pt이면 근거는 둘 다 모아 보여주되 신고는 한 번만 한다. 두 번 하면 한 문장이 위험 점수를 두 배로 받는다.

**② 자리는 근거가 아니다.**
머리말·꼬리말·주석에 있다는 이유만으로는 신고하지 않는다. 모든 문서에 머리말이 있다. 그 자리에서 색·크기 같은 실제 은닉 신호가 나와야 신고한다.

### 임계값을 정한 방법

감으로 정하지 않고 **테스트 문서 36개를 실제로 돌려서** 맞췄다. 놓치면 내리고, 정상 문서가 걸리면 올렸다.

| 폴더 | 개수 | 통과 조건 |
|---|---|---|
| `tests/hidden/` | 25개 | 여기서 **탐지돼야** 통과 |
| `tests/clean/` | 11개 | 여기서 **탐지 0건이어야** 통과 |

대조군(`clean/`)이 오탐을 막는 핵심이다. BOM 1개, 이모지 ZWJ, 추적 삭제 8개짜리 계약서 검토본처럼 **정상 문서에 흔한 것들**을 넣어서, 임계값을 낮출 때마다 오탐이 늘지 않는지 확인했다.

조정 기록은 1~8회차까지 `backend/scanner/tests/README.md`에 남겼다. 아래 한 줄로 재검증할 수 있다.

```bash
uv run python backend/scanner/tests/check_thresholds.py
```

### 회차별로 바뀐 것 (요약)

| 회차 | 내용 |
|---|---|
| 1~2 | 규칙을 코드로 만들고 A급 문자 기준을 3개 → 1개로 내림 |
| 3~4 | 확신도 계산 분리, 스펙에 있던 탐지 조건 3개 추가 |
| 5~6 | 코드만 있고 안 돌아본 경로 제거, 추적 삭제분 정책 확정 |
| 7 | 대조군 보강 — Bidi 임베딩과 재정의를 분리, 밀도 상한 추가 |
| 8 | 인젝션 모델 연결 후 "명령문"과 "계약 조항"이 섞이는 문제 수정 |

## 2.3 좌표 변환 (`parser/locate.py`)

탐지기는 "몇 번째 글자"로만 말하는데, PDF 마스킹은 **좌표로 지운다**. 그 사이를 잇는 파일이다.

### 왜 필요한가

PDF 안의 글자는 "몇 번째 문자"로 들어있지 않고 페이지 위 좌표에 하나씩 박혀 있다. 그래서 문자열 치환이라는 개념 자체가 성립하지 않고, 좌표로 지우는 수밖에 없다.

### 글자 수 비례로 짐작하면 안 되는 이유

줄 전체 사각형만 있으면 "10번째 글자"의 위치를 `줄 너비 ÷ 글자 수 × 10`으로 짐작하게 된다. 그런데 **한글은 약 10.3pt, 영문은 약 6.7pt로 폭이 1.5배 차이**라 섞인 줄에서는 밀린다.

실측: `담당자 연락처는 010-1234-5678 입니다`에서 11.4pt(글자 1.5개분) 어긋났다. 덜 덮이면 개인정보가 남고, 넓히면 옆 글자가 지워진다. 그래서 파싱 단계에서 글자별 가로 경계를 미리 뽑아 둔다.

### 줄바꿈 처리

값 하나가 두 줄에 걸치면 사각형이 둘 필요하다. 합집합 하나로 지우면 그 사이 멀쩡한 글자까지 지워진다.

- `Finding.bbox` — 합집합 사각형 1개 → **화면 하이라이트용**
- `evidence["rects"]` — 정밀 사각형 목록 → **실제 삭제용**

## 2.4 마스킹 사본 (`masking/mask.py`)

탐지가 끝난 결과를 받아 **원본 형식 그대로** 값만 가린 사본을 만든다. 원본 파일은 절대 건드리지 않고 항상 새 파일을 쓴다.

### 형식별 처리 방법

| 형식 | 방법 |
|---|---|
| TXT / MD / CSV | 문자열 치환 |
| DOCX | run 단위 치환 (글꼴·색·표·머리말 유지) |
| XLSX | zip 안에서 **글자가 든 XML만** 교체 |
| PDF | PyMuPDF 리댁션 (좌표로 실제 삭제) |
| 이미지 | 탐지된 영역을 덮고 유형 라벨 표시 |
| 스캔본 PDF | 페이지를 그림으로 구운 뒤 이미지와 같은 방식 |

### 주요 결정

**치환 문구에 유형을 남긴다.**
`홍길동` → `****`가 아니라 `[이름]`. `****`로 뭉개면 그 사본을 AI에 넣었을 때 문맥이 무너져서 요약이 망가진다. 유형을 남기면 GPT가 문서 구조를 그대로 이해한다.

**XLSX는 openpyxl로 저장하지 않는다.**
openpyxl은 워크북을 자기가 이해한 만큼 다시 써낸다. 그래서 매크로·피벗 캐시·폼 컨트롤이 사본에서 통째로 빠진다(실측 확인). zip을 직접 열어 고칠 XML만 바꾸고 나머지는 바이트 그대로 넘긴다 — 손대지 않은 것은 정의상 그대로 남는다.

**PDF는 덮지 않고 실제로 지운다.**
검은 사각형으로 덮기만 하면 복사·추출로 되살아난다. `apply_redactions()`로 콘텐츠 스트림에서 제거한다. 또한 증분 저장을 쓰지 않는다 — 증분 저장은 원본 바이트를 남겨둬서 지운 글자가 이전 판본으로 파일에 그대로 남는다.

**가릴 수 없으면 사본을 만들지 않는다.**
"일단 복사해두고 나중에"를 하지 않는다. 안 가려진 사본이 "마스킹 사본"이라는 이름을 달고 나가는 것은 아무것도 안 하느니 나쁘다. 가릴 수 없으면 `None`을 돌려준다.

### 해결한 문제

- **PDF 한글 폰트** — `add_redact_annot()`을 그냥 쓰면 대체 문자열이 `[????]`로 나온다. 저장소의 NanumGothic을 물리려 했지만 이 함수에는 fontfile 인자가 없고, `insert_font`로 심은 이름도 거부된다. 내장 CJK 폰트 `"korea"`를 쓰면 제대로 찍힌다.
- **워드 공백 유실** — 가리고 남은 글자가 공백으로 시작/끝나면 워드가 그 공백을 버린다. `xml:space="preserve"`를 붙여서 해결했다.
- **PDF 그림 훼손** — 리댁션 기본값은 사각형에 닿은 그림의 픽셀도 지워서, 글자 뒤에 있던 로고에 구멍이 뚫린다. 이미지·선 그림은 건드리지 않도록 옵션을 지정했다.

### 공통 안전장치

네 형식 모두, 사본을 만든 뒤 **그 사본을 다시 열어서 글자를 뽑아본다.** 거기서 가려야 할 값이 나오면 사본을 삭제하고 실패로 처리한다. 반쯤 가려진 파일이 임시 폴더에 남으면 언젠가 "마스킹 사본"으로 집어질 수 있기 때문이다.

## 2.5 오탐 제거 분류기 학습·평가 데이터

A의 분류기가 학습할 데이터를 만들었다. 형식은 A가 정한 규격(`text`, `type`, `start`, `end`, `label`, `group_id`)을 따랐다.

| 파일 | 건수 | 용도 |
|---|---|---|
| `false_positive_B_0913_001.json` | 344건 | 학습 |
| `false_positive_eval_B_0915_final.json` | 120건 | 평가 |

### 데이터를 만들 때 신경 쓴 것

**같은 템플릿에는 같은 `group_id`를 준다.**
"입금 계좌는 {값}입니다"에서 값만 바꾼 변형들은 한 그룹이다. 이게 있어야 A가 `StratifiedGroupKFold`로 학습·평가를 나눌 때 같은 문장이 양쪽에 걸치지 않는다. 그게 없으면 성능이 실제보다 부풀려진다.

**진짜와 형태만 같은 오탐을 짝으로 만든다.**
계좌번호 vs 주문번호·사번·송장번호처럼, 숫자만 봐서는 절대 구분할 수 없고 주변 단어를 봐야 갈리는 쌍을 타입별로 균형 있게 넣었다.

**사번이 자리를 먼저 선점하는 문제를 반영했다.**
`rules.py`에 사번 탐지기가 들어오면서 "사번 XXX"는 사번으로 먼저 잡히고 계좌번호 후보가 아예 안 된다. 생성기가 이 구조를 반영하도록 수정했다.

모든 값은 Faker 또는 직접 만든 생성기로 만들었고 실제 개인정보는 한 건도 쓰지 않았다.

## 2.6 검증 도구

스캐너가 "돌아간다"와 "제대로 돌아간다"는 다르다. 눈으로 확인할 수 없는 것들을 자동으로 점검하는 도구를 만들었다.

### `check_thresholds.py` — 숨은 텍스트 임계값 점검

테스트 문서 36개를 전부 돌려서, 숨긴 문서는 잡히고 정상 문서는 안 잡히는지 확인한다. 임계값을 고칠 때마다 이걸 돌려서 오탐이 늘지 않는지 봤다.

### `mask_check.py` — 마스킹 사본 점검

사본에서 확인하는 것:

1. 탐지된 값이 문자열로 남아있지 않은가 (가장 중요)
2. placeholder가 `****`가 아니라 `[이름]` 형태로 들어갔는가
3. 원본 파일이 바이트 단위로 그대로인가
4. 줄바꿈·BOM이 보존됐는가 (윈도우 `\r\r\n` 사고 방지)
5. 겹친 구간이나 범위 밖 offset을 흘리지 않는가

### `classifier_position_check.py` — 분류기 위치 버그 감시

**실제로 버그를 하나 찾아냈다.**

오탐 제거 분류기는 값을 `__VALUE__`로 바꾼 문장을 보고 판단한다. 그래서 자리가 틀리면 모델이 아예 다른 문장을 보게 된다.

```
정답   "입금 계좌는 512-... 이고 전표번호 __VALUE__ 은 회계 참조용입니다"  → 오탐 판정
틀림   "입금 계좌는 __VALUE__ 이고 전표번호 512-... 은 회계 참조용입니다"  → 진짜 판정
```

`filter_false_positive()`가 `start`/`end`를 인자로 받지 않고 문장에서 값을 다시 찾는데, `find()`는 **항상 첫 번째 위치**를 돌려준다. 같은 값이 한 문장에 두 번 나오면 두 번째가 첫 번째 자리로 판정된다.

**이 버그가 위험한 이유:** 학습할 때는 `start`/`end`를 정확히 들고 있어서 문제가 없다. 추론에서만 어긋나므로 **지표에는 전혀 나타나지 않고 실전에서만 틀린다.**

실행 결과 3건이 실패했다(2026-09-14 기준). 표·목록형 문서에서 같은 번호가 두 번 나오는 경우가 흔해서 실제 영향이 있다. B-2에게 전달했다.

점검 방식은 함수 시그니처가 아니라 **모델이 실제로 받은 문장**을 확인한다(`predict_proba`를 가로챔). 그래서 내부 구현이 바뀌어도 이 점검은 계속 유효하다.

## 3. 트러블슈팅

### 3.1 PDF는 "찾아 바꾸기"가 아예 안 된다

**문제**

TXT·DOCX·XLSX는 글자를 찾아서 바꾸면 끝난다. 그런데 PDF 안의 글자는 "몇 번째 문자"로 들어있는 게 아니라 **페이지 위 좌표에 하나씩 박혀 있다.** 문자열 치환이라는 개념 자체가 성립하지 않아서, 좌표로 지우는 방법밖에 없었다. 그리고 그 과정에서 문제가 하나씩 연달아 터졌다.

**① 검은 박스로 덮으면 복사하면 되살아난다**

처음엔 탐지된 자리에 검은 사각형을 그렸다. 그런데 그 위에서 드래그해서 복사하면 글자가 그대로 나온다. 화면만 가린 것이지 파일에서는 지워지지 않았다.
→ PyMuPDF의 `apply_redactions()`로 바꿔서, 사각형 안의 글자를 콘텐츠 스트림에서 **실제로 제거**했다.

**② 지웠는데 파일에 남아 있다**

실제 삭제로 바꿨는데도 값이 남았다. 원인은 저장 방식이었다. 증분 저장(incremental)은 원본 바이트를 그대로 두고 뒤에 변경분만 붙이는 방식이라, **지운 글자가 이전 판본으로 파일 안에 남는다.**
→ 증분 저장을 끄고 전체 재작성으로 저장했다.

**③ 한글 대체 문구가 `[????]`로 나온다**

`[전화번호]`를 넣었는데 사본에는 `[????]`가 찍혔다. PyMuPDF 기본 폰트에 한글 자형이 없어서였다. 저장소의 나눔고딕을 물리려 했지만 `add_redact_annot()`에는 fontfile 인자가 아예 없었고, `insert_font()`로 미리 심어둔 이름을 넘기니 "지원하지 않는 폰트"로 거부당했다.
→ 내장 CJK 폰트 `"korea"`를 쓰니 정상적으로 찍혔다.

**④ 글자 뒤 로고에 구멍이 뚫린다**

리댁션 기본값은 사각형에 닿은 **그림의 픽셀까지** 지운다. 그래서 글자 뒤에 있던 회사 로고에 흰 구멍이 생겼다.
→ 이미지와 선 그림은 건드리지 않도록 옵션을 지정했다.

**⑤ 두 줄에 걸친 값이 멀쩡한 글자까지 지운다**

전화번호가 줄 끝에서 잘려 `010-1234-`와 `5678`로 나뉘면 사각형이 두 개 필요하다. 그런데 둘을 감싸는 큰 사각형 하나로 지우면 **그 사이에 있는 다른 글자까지 사라진다.**
→ 좌표를 목록으로 돌려주도록 바꾸고, 화면 하이라이트용(합집합 1개)과 실제 삭제용(정밀 목록)을 분리했다.

**남은 교훈**

"가린 것처럼 보이는 것"과 "실제로 가려진 것"은 다르다. 그래서 마스킹이 끝나면 **사본을 다시 열어서 글자를 뽑아보고**, 가려야 할 값이 나오면 사본을 삭제하도록 만들었다.

### 3.2 사번(emp_no)을 어디서 빼야 하는가

> 모델 학습과 성능 지표는 A 담당이다. 여기 적는 것은 **학습 데이터 제작과 실측으로 확인한 부분**이다.

**문제**

오탐 제거 분류기의 성능이 기대보다 낮았고, 타입별로 보니 사번이 특히 나빴다. 원인을 찾아보니 사번은 회사마다 형식이 제각각(`S8905`, `2024-0317-05`, `EMP-03250`)이라 **표준 형식도 체크섬도 없었다.** 모델이 값에서 배울 게 없으니 대신 **우리가 만든 합성 문장의 표현을 외우고 있었다.** 학습 데이터 스타일에만 맞는 모델이 된 것이다.

그래서 사번을 모델 학습 대상에서 빼기로 했다.

**빼면서 부딪힌 문제**

"모델이 못 배우는 타입이면 탐지기에서도 빼면 되지 않나?" 싶어서 `rules.py`의 사번 탐지기를 제거해봤다. 결과는 더 나빴다.

```
"사번 2024-0317-05 직원의 근태 규칙 위반 건"
       └────┬────┘
   사번 탐지기가 없으면 → 계좌번호 형식과 똑같이 생겨서 account로 잡힘
   화면에 "계좌번호 2024-0317-05"로 표시되고, 위험점수도 10점 → 30점으로 3배 부풀려짐
```

사번 탐지기에는 탐지 말고 **자리 선점**이라는 본업이 따로 있었다. 사번이 그 구간을 먼저 잡아두지 않으면 계좌번호 탐지기가 가져가버린다.

**해결**

단계를 나눠서 처리했다.

| 단계 | 처리 |
|---|---|
| 찾기 (`rules.py`) | **그대로 유지** — 자리 선점이 필요하므로 |
| 거르기 (`models.py`) | 모델에는 **안 물어봄** — 학습하지 않은 타입 |

대신 사번 오탐 중 가장 흔한 패턴 하나를 규칙으로 대체했다. "이건 예시다"라고 문장이 직접 말해주는 경우다.

```
"사번 S8905 형식으로 자동 부여됩니다"   ← 진짜 사번이 아니라 형식 설명
```

**규칙의 창 크기도 실측으로 정했다.** 처음엔 문장 전체에서 `예시·형식·양식·규칙` 같은 단어를 찾았는데, 그러면 진짜 사번이 든 문장 12건 중 10건이 잘못 걸렸다.

```
"사번 2024-0317 직원의 근태 규칙 위반 건"     ← '규칙'은 근태에 붙은 말
"사번 EMP-03250 님의 연차 신청 양식을 반려"    ← '양식'은 신청에 붙은 말
```

→ **값 바로 뒤 12글자까지만** 보도록 좁혔다. 결과는 예시 문장 36건 중 32건(88.9%)을 걸러내고, 진짜 사번은 하나도 버리지 않았다. 못 거르는 4건은 마커가 값에서 떨어져 있는 경우인데, 창을 넓히면 위의 진짜 문장들이 걸리기 시작해서 넓히지 않았다. **예시가 덜 걸리는 쪽이 진짜 사번을 버리는 쪽보다 낫다**고 판단했다.

**남은 것**

전화번호도 성능이 낮은데(holdout 누락률 25%), 원인은 문맥 데이터 부족으로 좁혔고 아직 해결하지 못했다. 장비번호·품목코드·접수번호처럼 형태가 비슷한 오탐 데이터를 보강해야 한다.

### 3.3 탐지 0건은 근거가 아니었다

**문제**

숨은 텍스트 탐지는 우리 서비스의 차별점인 만큼, 오탐이 나면 신뢰가 통째로 무너진다. 그래서 1~2회차에 임계값을 내리면서 이런 결론을 적어뒀다.

> "대조군의 A급 문자는 전부 0개다. A급은 정상 문서에 나올 이유가 없는 문자라서, 임계값을 3개 → 1개로 내려도 오탐이 늘지 않는다."

7회차 중간 점검에서 이 문장이 **아무것도 증명하지 못한다**는 것을 발견했다.

> **대조군에 A급 문자가 애초에 한 글자도 없었다.**
> 0이 나온 이유가 "규칙이 잘 걸러서"가 아니라 "시험할 대상이 없어서"라면, 그 0은 근거가 아니다.

그리고 실제로 오탐이 났다. **아랍 거래처 상호를 인용한 정상 계약서**가 확신도 0.9짜리 숨은 텍스트 2건으로 잡혀서 위험점수 38.1(노란불)이 됐다.

**원인**

A급으로 묶어둔 문자 9개의 성격이 사실 둘로 갈려 있었다.

| 문자 | 정상 문서에서 | 판정 |
|---|---|---|
| LRO · RLO | 유니코드가 쓰지 말라고 한 것. 내보내는 정상 편집기가 없다 | A급 유지 |
| 태그 문자 | 어떤 폰트로도 안 그려진다. 심는 것 말고 쓸 일이 없다 | A급 유지 |
| LRE · RLE · PDF | 아랍어·히브리어를 인용하면 워드·InDesign이 **그냥 넣는다** | Bidi급으로 분리 |
| LRI · RLI · FSI · PDI | 유니코드가 임베딩 **대신 쓰라고 권장**하는 표기 | Bidi급으로 분리 |

아래 네 개를 A급에 넣어둔 게 문제였다. 정상 문서에 흔히 들어가는 문자였던 것이다.

**해결**

A급을 "정말 쓸 일이 없는 문자"로 좁히고, 나머지를 Bidi급으로 분리했다. Bidi급은 개수가 아니라 **복원 검사를 통과해야만** 신고한다.

```
정상 인용문을 되돌리면  →  뒤집힌 글자만 나옴       → 신고 안 함
공격 문서를 되돌리면    →  지시문이 통째로 나옴     → 신고
```

그리고 **정상 샘플과 공격 샘플을 같은 호흡에 쌍으로 만들었다.** 임베딩을 정상적으로 쓴 계약서(`clean/09`)와, 같은 임베딩으로 글자 순서를 뒤집은 공격 문서(`hidden/23`)를 나란히 놓아서, 다음에 임계값을 건드릴 때 양쪽을 동시에 확인할 수 있게 했다.

**교훈**

이 일 이후로 원칙을 하나 세웠다. **탐지 범위를 넓힐 때는 오탐을 억제하는 장치를 같은 호흡에 내놓는다.** 정상 문서 샘플이 없는 상태에서 "오탐이 안 늘었다"고 말하는 것은 측정이 아니라 희망이다.

대조군을 11개까지 늘린 것도 이 때문이다. BOM 1개, 이모지 ZWJ, 추적 삭제 8개짜리 계약서 검토본처럼 **정상 문서에 실제로 흔한 것들**을 모아서, 임계값을 내릴 때마다 여기서 0건이 유지되는지 확인한다.

## 7. 발표용 핵심 설명

### 왜 서식까지 보는가

일반적인 개인정보 검사는 화면에 보이는 텍스트만 읽는다. 그런데 흰 배경에 흰 글씨, 0pt 글자, PDF 렌더 모드 3은 **화면에는 안 보이면서 파일 안에는 남아 있고, AI에 넣으면 그대로 읽힌다.** 기존 검사 도구가 다루지 않는 영역이라 여기가 우리 서비스의 차별점이다.

### 왜 원본을 고치지 않는가

탐지 결과는 "몇 번째 글자부터 몇 번째까지"라는 숫자 위치로만 기록된다. 파서가 줄바꿈 하나만 정규화해도 그 숫자가 전부 밀려서, 화면 하이라이트는 엉뚱한 글자에 그려지고 마스킹은 멀쩡한 글자를 지운다. 그래서 파서의 철칙은 "원문을 한 글자도 고치지 않는다"다.

### 왜 `****`가 아니라 `[이름]`인가

마스킹 사본의 용도 중 하나가 "AI에 안전하게 넣기"다. `****`로 뭉개면 문맥이 무너져서 요약이 망가진다. 유형을 남기면 AI가 문서 구조를 그대로 이해해서 정상적으로 동작한다.

### 왜 못 가리면 사본을 안 만드는가

반쯤 가려진 파일이 "마스킹 사본"이라는 이름을 달고 나가면, 사용자는 안전한 줄 알고 그것을 어디든 보낸다. 아무것도 안 하는 것보다 나쁘다. 그래서 완벽하게 가리거나 아무것도 안 내놓거나 둘 중 하나다.

### 임계값을 어떻게 정했는가

감으로 정하지 않았다. 숨긴 문서 25개와 정상 문서 11개를 만들어 8회에 걸쳐 돌리면서, 놓치면 내리고 정상 문서가 걸리면 올렸다. 특히 대조군(정상 문서)을 먼저 준비한 것이 핵심이다. 숨긴 문서만 보고 임계값을 내리면 탐지율은 오르지만 멀쩡한 문서가 전부 빨간불이 된다.
