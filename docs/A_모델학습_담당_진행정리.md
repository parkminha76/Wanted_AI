> **기준일:** 2026-09-13  
> **프로젝트:** 2026 원티드 AI Championship — 정보유출 스캐너 + 사기 대응 훈련 모드

## 1. 담당 범위

A의 기본 담당은 모델 학습과 합성 데이터 생성이다. 팀에 별도 D 담당이 없는 상황이라 심사위원용 데모 파일과 화면 구성 검토도 일부 함께 진행했다. DB는 원래 담당 범위가 아니었지만, 개인정보를 다루는 서비스 특성상 privacy-first 설계와 모델 결과 저장 규칙을 추가로 점검했다.

### 핵심 담당

- 신분증 이미지 탐지 CNN(YOLO) 학습 및 모델 전달
- Faker·Custom Generator 기반 합성 개인정보 생성
- 체크섬 및 형식 검증 함수 작성
- 오탐 제거 분류기 학습·평가
- 프롬프트 인젝션 분류기 학습·평가
- 모델 파일, 사용법, 데이터 요청 규격을 B·C에게 전달

### 추가로 진행한 범위

- DB v3 privacy-first 설계 검토 및 저장 데이터 검증 기준 정리
- 심사위원용 데모 파일 4종 생성 및 품질 개선
- 프론트 화면 구성과 데모 흐름 검토
- 모델과 스캐너 사이의 실제 호출 경로 점검

## 2. 완료한 작업

## 2.1 신분증 CNN(YOLO)

- 신분증 이미지 필드 탐지용 YOLO 모델 학습 완료
- 검증 성능이 가장 좋았던 `best.pt`를 배포·통합용 모델로 정리
- 최종 전달 경로: `ml/models/infoguard_cnn_v1.pt`
- B가 바로 로드할 수 있도록 모델 핸드오프 가이드 작성
- 학습 산출물 전체가 아니라 실제 추론에 필요한 최종 가중치만 전달하도록 정리
- 얼굴 사진, 서명, 신분증 메타정보 등 공용 `RiskType`과 연결 가능한 구조 확인

### 현재 상태

- **모델 학습 및 1차 전달 완료**
- 회전된 신분증에 대한 augmentation 재학습은 선택 개선 항목으로 남아 있음
- 본선 또는 시간이 남을 경우 회전·원근·조도 변화 데이터를 추가해 재학습 가능

## 2.2 합성 데이터와 체크섬 검증

실제 개인정보와 실제 신분증을 사용하지 않는 원칙으로 데이터 생성 파이프라인을 구성했다.

### 구현 내용

- Faker 기반 이름·주소·전화번호 등 합성 정보 생성
- Custom Generator 구현
  - 운전면허번호
  - 외국인등록번호
  - 사업자등록번호
  - 계좌번호
- 체크섬 검증 함수 구현
  - `rrn`: 주민등록번호
  - `foreign_reg`: 외국인등록번호
  - `biz_reg`: 사업자등록번호
  - `card`: Luhn 알고리즘
- 검증 가능한 값과 형식만 확인 가능한 값을 명확히 구분
  - 계좌번호: 은행별 자릿수만 확인 가능
  - 운전면허번호: 공개 체크섬이 없어 형식만 확인
  - 여권번호: 인쇄 번호 자체에는 체크 디지트가 없어 형식만 확인
  - 사번: 회사별 규칙이 달라 공통 검증 불가

### 중요한 수정

`get_checksum_feature()`가 문장 전체를 validator에 넘기던 문제를 수정했다. 현재는 `text[start:end]`로 추출한 실제 후보값만 검증한다.

```python
value = text[start:end]
validator(value)
```

문장 전체를 넘기면 한글과 공백 때문에 자릿수 검증부터 실패해 체크섬 feature가 사실상 동작하지 않는다. 이 수정으로 학습과 실제 스캐너 추론이 같은 후보값 기준을 사용한다.

## 2.3 오탐 제거 분류기

정규식이 찾은 값이 실제 개인정보인지, 형식만 비슷한 주문번호·송장번호·쿠폰번호인지 문맥으로 구분하는 모델을 구현했다.

### 모델 구성

- Kiwi 토큰 기반 단어 TF-IDF
- 문자 3~5-gram TF-IDF
- `RiskType` 원-핫 인코딩
- 타입과 문맥을 결합한 feature
- 후보값 체크섬 feature
- Logistic Regression
- 동일 템플릿이 학습·검증에 나뉘지 않도록 `StratifiedGroupKFold` 적용

### 학습 대상

- `account`
- `biz_reg`
- `card`
- `phone`

`emp_no`는 회사마다 형식이 다르고 합성 문장 표현을 외우는 문제가 확인되어 모델 대상에서 제외했다. 스캐너에서는 사번 후보를 분류기에 넣지 않고 기존 규칙 결과를 그대로 통과시킨다.

### 학습 데이터와 교차검증

- 모델 대상 학습 데이터: 272건
- 제외된 `emp_no`: 72건
- 선택된 `C`: 16.0
- F1@0.5: **0.8837**
- ROC-AUC: **0.9538**
- PR-AUC: **0.9551**
- 운영 임계값: **0.353372**
- 교차검증 기준 개인정보 후보 누락률: **4.62%**

운영 임계값은 F1 최대값이 아니라 개인정보 누락률을 5% 이하로 제한하는 기준으로 선택했다. 오탐이 조금 늘더라도 실제 개인정보를 오탐으로 제거해 마스킹에서 빠뜨리는 위험을 줄이기 위한 결정이다.

### 별도 holdout 평가

- 평가 데이터: 64건
- Precision: **0.8108**
- Recall: **0.9375**
- F1: **0.8696**
- FNR: **6.25%**
- ROC-AUC: **0.9639**
- PR-AUC: **0.9758**

| 타입 | F1 | 누락률 |
|---|---:|---:|
| account | 1.0000 | 0% |
| biz_reg | 0.8889 | 0% |
| card | 0.9412 | 0% |
| phone | 0.6667 | 25% |

전화번호가 현재 핵심 약점이다. Holdout 전체 누락 2건도 전화번호에서 발생했다.

평가 파일은 학습 glob에서 제외하도록 로더를 수정했다. 다만 동일 문장 중복은 없지만 64건 중 48건이 학습셋과 같은 `group_id`와 유사 문장 틀을 사용하므로, 완전히 독립된 실문서 평가라고 표현하지 않고 **holdout 문장 평가**로 기록했다.

### 현재 상태

- **분류기 코드, 저장 모델, 스캐너 연결 완료**
- **운영 임계값 적용 완료**
- 전화번호 문맥 데이터 보강 필요
- 실제 문서 구조에서 가져온 완전 독립 평가셋 필요

## 2.4 프롬프트 인젝션 분류기

문장이 AI의 기존 지시를 바꾸거나 정보 출력·역할 변경·안전장치 우회를 요구하는지 판별하는 이진 분류기를 구현했다.

### 데이터 구성

- 전체 491건
- 429개 그룹
- 정상 문장: 296건
- 인젝션 문장: 195건
- Lv.1~5 포함
- 영문 데이터 40건 포함
- 동일 문장 중복 0건
- label 충돌 0건

`level`, `source`, `attack_type`은 평가 분석용 메타데이터이며 실제 모델 feature로 사용하지 않는다. 실제 서비스 입력에는 문장만 들어오기 때문이다.

### 최신 교차검증 결과

- Precision: **0.8600**
- Recall: **0.8821**
- F1: **0.8709**
- ROC-AUC: **0.9579**
- PR-AUC: **0.9486**

| 레벨 | F1 |
|---|---:|
| Lv.1 | 0.9184 |
| Lv.2 | 0.8224 |
| Lv.3 | 0.8108 |
| Lv.4 | 0.9744 |
| Lv.5 | 0.9500 |

### 확인된 문제

Lv.2~3 데이터 일부가 AI 대상 프롬프트 인젝션이 아니라 사람 대상 피싱·송금 요청으로 작성되어 있었다.

예를 들어 아래 문장은 사기 훈련 시나리오에서는 공격 문장이지만, AI의 지시를 변경하는 프롬프트 인젝션은 아니다.

- 첨부파일을 다운로드해 달라는 요청
- OTP를 입력해 달라는 요청
- 변경된 계좌로 송금해 달라는 요청
- 임원 지시라며 긴급 처리를 요구하는 문장

반대로 보안교육 자료에서 공격 문장을 인용한 정상 문서는 `규칙 무시`, `정보 출력`, `보안 해제` 등의 단어 때문에 인젝션으로 오인되는 문제가 있었다.

### 출처별 확인 결과

- 일반 업무문서 오탐률: **7.3%**
- 보안교육 공격 인용문 오탐률: **25%**
- 한국어 공격 문장 누락률: **11.4%**
- 영문 공격 문장 누락률: **15%**

### 현재 상태

- **1차 분류기 및 저장 모델 완료**
- Lv.4~5와 영문 데이터 반영 완료
- Lv.2~3 label 기준 재검수 필요
- 사람 대상 피싱 문장은 훈련 시나리오 데이터와 분리 필요
- 공격 문장과 보안교육 인용문을 대조쌍으로 보강한 뒤 재학습 필요

## 2.5 스캐너 연동 점검

모델 파일만 전달하는 데서 끝내지 않고 실제 스캐너 경로에서 다음 사항을 확인했다.

- `filter_false_positive()`에 문장 전체와 정확한 `start/end`가 전달되는지 확인
- 분류기가 `False`를 반환하면 finding 제거와 마스킹 제외로 이어지는 흐름 확인
- 모델이 학습하지 않은 타입은 기존 탐지 결과를 그대로 통과하도록 처리
- `emp_no` 분류기 우회 확인
- 저장된 운영 임계값을 스캐너가 실제로 사용하는지 테스트
- 인젝션 모델이 없을 때 fallback하고, 모델이 있을 때 저장 모델을 사용하는 구조 확인
- `injection_pattern_match` 경로가 도달하지 않던 문제 확인 및 수정
- 저장 모델 로드와 통합 관련 테스트 7개 통과

### B에게 전달한 최종 확인 항목

1. 후보값과 정확한 `start/end`가 분류기에 전달되는지
2. 오탐 제거 결과가 finding과 마스킹 사본에 동일하게 반영되는지
3. 미학습 타입이 기존 규칙 결과를 유지하는지
4. 모델 파일이 없는 환경에서도 전체 스캔이 중단되지 않는지

## 2.6 DB privacy-first 설계 보완

DB는 원래 A의 기본 담당이 아니었지만 개인정보 원문이 저장되는 위험을 막기 위해 v3 설계 검토에 참여했다.

### 반영한 원칙

- 업로드 원문과 마스킹 사본을 DB에 저장하지 않음
- Finding의 화면용 `reason` 자유 텍스트를 DB에는 그대로 넣지 않고 고정 코드로 변환
- `session_id`를 익명화라고 표현하지 않고 **익명 방문자 세션 식별자**로 정의
- `company_admin` 권한은 `session_id`만으로 신뢰하지 않고 별도 인증·인가가 필요함을 명시
- `hidden_commands.scan_result_id`를 제거하고 `finding_id`만 유지
- 부모 삭제 시 자식 레코드가 함께 삭제되도록 FK `ON DELETE CASCADE` 적용
- JSON 컬럼에 리터럴 DB DEFAULT가 있다고 오해할 표현 제거
- 애플리케이션 converter가 JSON dict를 명시적으로 전달하도록 정리
- `RiskType` 허용값을 `backend/shared/schema.py`에서 직접 가져오도록 단일화
- `FindingRow.type`, `TrainingEvent.detected_field`, `finding_counts` 키 검증
- `finding_counts` 값이 0 이상의 정수인지 검증
- evidence의 타입·범위·모델명·체크섬 값을 화이트리스트로 검증
- ORM 속성 재할당과 converter 검증 범위, bulk SQL이 우회하는 범위를 문서화
- dict 내부를 직접 변경하지 않도록 `set_evidence()`, `add_finding_count()` 형태의 재할당 helper 정리
- `TrainingEvent.detected_field=None`은 탐지 결과가 없는 정상 이벤트로 허용하는 의도 확인

### 남은 확인

- B·C 코드가 `converters.py` 경로를 일관되게 사용하는지
- bulk insert 또는 직접 SQL 저장 경로가 새로 생기지 않았는지
- 보존 정책이 문서에만 존재하지 않고 실제 배포 스케줄에서 실행되는지
- DB 통합 검증은 프론트·백엔드 연결 이후 별도로 진행

## 2.7 심사위원용 데모 파일

`GET /samples`에서 즉시 체험할 수 있도록 실제 업무 문서처럼 보이는 합성 샘플을 제작했다.

| 파일 | 구성 | 주요 탐지 대상 |
|---|---|---|
| `고객명단.xlsx` | 고객 24명, 고객 현황·운영 요약·열람 안내 3개 시트 | 이름, 전화번호, 이메일, 주소 |
| `개발문서.md` | 고객 포털 배포 인수인계 문서 | API 키, GitHub 토큰, DB 접속정보 |
| `계약서.pdf` | 3페이지 용역계약서 | 사업자번호, 계좌번호, 연락처, 이메일 |
| `숨은명령.docx` | 3페이지 협력사 정산 안내문 | 흰색 1pt 프롬프트 인젝션, 연락처 |

### 검증 내용

- 모든 개인정보·기업·금융정보는 Faker 또는 합성값
- XLSX 각 시트 렌더링 및 셀 잘림 확인
- PDF 한글 글꼴을 TTF로 포함해 뷰어 호환성 개선
- DOCX A4 3페이지 렌더링 확인
- 숨은 명령이 화면에서는 보이지 않고 스캐너에서는 인젝션 1건으로 탐지되는지 확인
- `/samples`에서 파일 4개가 오류 없이 반환되는지 확인

## 3. B·C 협업을 위해 정리한 내용

### B — 오탐 제거 데이터 및 스캐너

- 데이터 형식: `text`, `type`, `start`, `end`, `label`, `group_id`
- `type`은 `backend/shared/schema.py`의 `RiskType` 값을 사용
- 실제 개인정보가 아닌 Faker·합성값만 사용
- 진짜 개인정보와 형태만 같은 오탐을 타입별로 균형 있게 구성
- 모델 전달 후 스캐너 호출·제거·마스킹 경로 확인 요청

### C — 인젝션 데이터 및 훈련 모드

- 데이터 형식: `text`, `label`, `level`, `source`, `group_id`
- `label=1`은 AI 대상 지시라는 기준 유지
- 훈련 시나리오의 Lv.1~5를 평가 구간으로 사용
- 사람 대상 피싱 문장과 AI 대상 프롬프트 인젝션을 구분
- 정중한 요청, 긴급성 부여, 시스템 메시지 위장, 역할 변경 등 다양한 공격 표현 요청
- 보안교육에서 공격 문장을 인용한 정상 문서도 hard negative로 요청

## 6. 발표용 핵심 설명

### 직접 학습한 AI가 필요한 이유

정규식은 형식만 보기 때문에 계좌번호와 주문번호처럼 숫자 구조가 같은 값을 구분하기 어렵다. docXray는 정규식 후보를 문맥 분류기로 다시 검토해 오탐을 줄인다. 문서 속 프롬프트 인젝션도 단순 금칙어가 아니라 문장 단위 분류기로 판단한다.

### 개인정보 누락률을 우선한 이유

주문번호를 개인정보로 남기는 오류는 사용자가 확인할 수 있지만, 실제 개인정보를 오탐으로 제거하면 마스킹 사본에 원문이 남을 수 있다. 따라서 오탐 제거 모델은 F1 최대 지점보다 개인정보 후보 누락률을 제한하는 운영 임계값을 사용한다.

### 데이터 안전성을 확보한 방법

모델 학습과 시연에는 실제 개인정보를 사용하지 않는다. Faker, 직접 구현한 Custom Generator, 공개 체크섬 알고리즘을 이용해 형식적으로 유효한 합성값만 생성한다. 업로드 원문은 DB에 저장하지 않고 탐지 타입·개수·위험점수 같은 구조화된 결과만 남긴다.

### 현재 한계를 숨기지 않는 이유

합성 데이터 성능은 실제 운영 성능과 같지 않다. 오탐 제거 모델은 전화번호 문맥이 약하고, 인젝션 모델은 사람 대상 사기 문장과 AI 대상 명령의 경계 및 보안교육 인용문 처리에 한계가 있다. 평가 방식과 데이터 한계를 함께 공개하고 다음 개선 항목으로 관리한다.
