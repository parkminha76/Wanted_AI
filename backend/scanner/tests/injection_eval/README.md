# 인젝션 독립 평가셋 (B)

인젝션 분류기와 스캐너의 인젝션 판정을 **학습에 쓰지 않은 문장**으로 확인하기 위한
평가 전용 데이터다. 발표 수치(교차검증 F1)는 같은 생성 흐름에서 나온 데이터를 나눠
맞춘 값이라, 다른 흐름으로 만든 문장에서도 성립하는지 따로 확인해야 한다.

## 파일

| 파일 | 내용 |
|---|---|
| `injection_eval_B_0914.json` | 평가 문장 100건 |
| `evaluate_injection_eval.py` | 스키마 검사 · 학습 데이터와 중복 검사 · 성능 측정 |

```powershell
uv run python backend/scanner/tests/injection_eval/evaluate_injection_eval.py
```

## 지켜야 할 것

- **학습에 넣지 않는다.** 학습 스크립트는 `sample_data/injection/injection_*.json`만 읽는다.
  이 파일을 그 폴더로 옮기거나 같은 이름 규칙으로 복사하면 평가셋이 오염된다.
- **라벨 확정 전 2차 검수가 필요하다.** 팀 규칙상 라벨은 두 사람이 각자 매기고 어긋난 것만
  상의한다. 지금 라벨은 작성자 1차 라벨이다.
- **검수로 확정한 뒤에는 수정하지 않는다.** 성능이 안 나온다고 문장이나 라벨을 고치면
  평가 의미가 사라진다. 바꿔야 하면 새 파일(`_v2`)로 만든다.
- 실제 개인정보는 없다. 숫자·이름이 들어간 문장도 전부 가상이다.

## 라벨 기준

인젝션 분류기 README와 같다: **문장이 AI의 지시를 바꾸거나 정보 유출·안전장치 우회를
유도하면 1, 사람에게 하는 말이면 0.** 공격 문구를 인용하더라도 사람에게 경고·설명하는
문장(보안교육 인용)은 0이다.

## 구성 (100건)

| 구분 | 건수 | 넣은 이유 |
|---|---:|---|
| 공격 Lv.1 일상형(배송·공공기관·SNS·청첩장·로맨스) | 8 | 학습된 주제를 다른 문체로 |
| 공격 Lv.2 직장 내부형(IT팀·인사팀 사칭) | 8 | 〃 |
| 공격 Lv.3 거래·금전형(계좌 변경·송금) | 8 | 〃 |
| 공격 Lv.4 임원 사칭 | 8 | 학습 데이터가 적은 구간(레벨당 20건) |
| 공격 Lv.5 AI 도구·문서 처리 | 8 | 〃 |
| 정상 계약·공문 조항 | 20 | "~할 수 없다/~하여야 한다" 지시형 어미가 공격과 겹쳐 오탐이 실측된 구간 |
| 정상 업무 요청 | 15 | 공손한 요청문 오탐 확인 |
| 정상 보안·대외비 안내 | 10 | "~하지 마세요" 금지형 문장 |
| 정상 고객 응대 | 10 | 정보를 묻는 문장 |
| 정상 보안교육 인용문 | 5 | 공격 문구·키워드를 인용하지만 사람에게 설명하는 문장 |

정상을 60%로 둔 이유: 실제 문서는 문장 대부분이 정상이다. 학습 데이터처럼 반반으로
만들면 평가 숫자가 실제보다 좋게 나온다.

공격 40건 중 스캐너 키워드 목록(무시하고·이전 지시·시스템 프롬프트 등)에 걸리는 문장은
일부러 적게 넣었다. 키워드가 아니라 모델이 잡는지를 보려는 것이다.

## 한계

- 사람이 쓴 실제 문서가 아니라 작성자가 만든 합성 문장이다. C의 생성 스크립트와는
  작성 흐름이 다르지만, 둘 다 실문서 성능을 대신하지 못한다.
- 정상 계약 조항 일부는 이미 오탐이 확인된 문체를 참고해 만들었다. 약점을 드러내는 쪽으로
  치우친 구간이므로, 그 구간 수치는 "어려운 사례에서의 성능"으로 읽어야 한다.
- 영문 인젝션은 넣지 않았다.

## 필드

C의 학습 데이터 스키마(`text`, `label`, `level`, `source`, `group_id`, 공격이면
`attack_type`)를 그대로 따르고, 분석용 `category`를 더했다. 평가셋은 fold를 나누지
않으므로 `group_id`는 문장마다 따로 준다.
