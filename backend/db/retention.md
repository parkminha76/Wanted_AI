# 데이터 보존 기간 및 삭제 정책

## 보존 기간

| 데이터 | 보존 기간 | 삭제 방식 |
|---|---|---|
| `scan_results` + 자식(`findings`, `hidden_commands`) | 30일 | 배치 삭제 (아래 참고) |
| `training_progress` + `training_events` | 해커톤 데모 종료 시점까지 | 수동 또는 이벤트 종료 후 일괄 삭제 |
| `companies`, `scam_cases` | 무기한 (애초에 데이터 없음, 스키마만 존재) | 해당 없음 |

30일로 정한 근거: 원문 자체는 이미 저장 안 하므로 개인정보 재식별 리스크가
낮지만, `finding_counts`(유형별 개수)와 `session_id` 조합이 누적되면 특정
세션의 사용 패턴이 드러날 수 있어 무기한 보관은 피한다. 30일은 임의 값이며
필요시 팀 협의로 조정 가능.

## 삭제 순서

**`ON DELETE CASCADE`를 걸어뒀으므로 실무에서는 부모만 지우면 자식이 자동
삭제된다.** 순서를 직접 관리할 필요가 없다.

```sql
-- 이것만 실행하면 findings, hidden_commands가 자동으로 같이 삭제됨
DELETE FROM scan_results WHERE created_at < NOW() - INTERVAL 30 DAY;

-- training도 마찬가지로 training_progress만 지우면 training_events 자동 삭제
DELETE FROM training_progress WHERE completed_at < '2026-09-20';
```

배치 작업(cron)으로 돌릴 경우 이 두 DELETE문만 주기적으로 실행하면 된다.
2주 해커톤 스코프에서는 별도 스케줄러 없이 수동 실행으로도 충분하다.

## ⚠️ 스크립트 존재 ≠ 자동 실행

`db/retention_job.py`는 삭제를 **실행할 수 있는 수단**일 뿐이다. 누군가
(또는 스케줄러가) 그 스크립트를 주기적으로 돌리지 않으면 오래된 데이터는
계속 쌓인다. 아래 중 하나를 실제로 설정해야 "자동 만료"가 완성된다.

- **로컬/자체 서버로 배포한 경우**: 서버 crontab에 등록
  ```bash
  crontab -e
  # 매일 새벽 3시 실행
  0 3 * * * cd /path/to/repo && python -m backend.db.retention_job
  ```
- **Railway로 배포한 경우**: Railway의 Cron Job 기능(대시보드 → Cron
  Schedule)으로 별도 서비스를 등록. 일반 서버 crontab과 달리 컨테이너가
  상시 구동이 아니면 OS crontab 자체가 안 돌아갈 수 있으므로, 반드시
  플랫폼이 제공하는 스케줄러 기능을 쓸 것.
- **수동으로 갈 경우**: 최소한 제출 마감(9/20) 전, 그리고 심사 기간
  (~10/5) 중간에 한 번씩 직접 실행하는 것을 팀 일정에 캘린더로 박아둘 것.
  "언젠가 알아서 지워지겠지"라고 가정하면 안 됨 — 지금 이 스크립트는
  실행돼야만 지워진다.

지금 팀 상황(2주 해커톤, D 없음)에서는 마지막 "수동 실행 일정에 박아두기"
정도가 현실적인 선택지일 가능성이 높다. 그렇다면 담당자와 실행 날짜를
지금 정해둘 것.

## DB 설계만으로는 끝나지 않는 것 — 애플리케이션 레벨 체크리스트

"처리 후 즉시 폐기" 원칙은 DB 스키마만 지킨다고 완성되지 않는다. 아래는
**B(스캐너 엔진)가 구현 시 반드시 지켜야 하는 것**들이다.

- [ ] **임시 파일 정리**: 업로드된 원본 파일과 마스킹 사본은 처리 직후 즉시
      삭제한다. `try/finally`(또는 컨텍스트 매니저)로 감싸서, 스캔이
      **성공하든 실패하든 취소되든** 예외 없이 파일이 지워지게 만들 것.
      ```python
      try:
          result = scan_file(temp_path)
          return result.to_dict()
      finally:
          os.remove(temp_path)  # 성공/실패/예외 어떤 경우에도 실행됨
      ```
- [ ] **서버 로그에 원문 금지**: `logger.info(f"스캔 결과: {result}")`처럼
      전체 객체를 로그에 찍으면 raw_text가 로그 파일에 그대로 남는다.
      로그에는 `scan_id`, `risk_score`, `status` 같은 메타데이터만 남길 것.
- [ ] **예외 메시지에 원문 포함 금지**: 파싱 실패 시 `except Exception as e:
      logger.error(f"파싱 실패: {file_content}")`처럼 원문을 예외 로그에
      찍지 않을 것. `db/codes.py:derive_error_code()`가 DB 저장용 코드
      변환은 해주지만, 그 이전에 서버 로그 자체에 원문이 안 남게 하는 건
      별도로 신경 써야 한다.
- [ ] **임시 파일 저장 위치**: OS 임시 디렉토리(`/tmp` 등) 사용 시 다른
      프로세스가 읽을 수 없도록 권한을 제한할 것 (`0600` 등).
- [ ] **훈련 모드 답장 텍스트**: `scan_text()`에 들어가는 사용자 입력도
      함수 실행 후 메모리에서 참조가 끊기면 그만이지만, 혹시 별도로
      캐싱(Redis 등)하고 있다면 그 캐시에도 TTL을 짧게 걸어둘 것.

이 체크리스트는 DB 스키마가 아무리 잘 설계돼도, 실제 구현에서 로그 한 줄로
전부 무력화될 수 있다는 점을 상기하기 위한 것이다. B의 구현 리뷰 시 이
항목들을 같이 확인할 것.
